### Introduction

Your Chat With Your Docs system works on the questions you tried. Does it work on the questions your users will ask? In this project you will build an evaluation harness that answers that with numbers. You will write a dataset of 50 or more questions, including trick and out-of-scope questions, measure retrieval and answers separately, check that your LLM judge agrees with you, and then make one change to the system and show exactly how the scores moved.

This is the project that proves you can improve an AI system on purpose instead of by luck. Hiring managers look for it.

### Before you start

- Create a new GitHub repository called `mimir-rag-eval-harness` as a `uv` project. Install your Chat With Your Docs project as a dependency (for example `uv add git+https://github.com/<you>/mimir-chat-with-your-docs`) so the harness calls the same code your app uses. If you need to change that code, change it in the original repo.
- Make sure your RAG system can return, for any question, the answer, the cited sources and the list of retrieved chunk IDs. The harness needs all three.
- Decide whether to write the harness in plain Python, with promptfoo, with Ragas, or a mix. Plain Python is the most instructive; tools save time. Any choice is fine as long as you can explain every number it produces.

#### Write questions before you run them

Write the questions and reference answers from the documents, not from your system's outputs. If you write questions by looking at what the system already answers well, your scores will flatter it.

### Assignment

<div class="lesson-content__panel" markdown="1">

1. Build a dataset of at least 50 questions in `data/eval_set.jsonl`. Each entry has an ID, the question, a type, the IDs of the chunk or chunks that contain the answer, and a short reference answer. Include at least:
   - 30 normal answerable questions, a mix of easy and hard.
   - 8 trick questions, such as false premises ("Why does version 2 remove feature X?" when it does not), questions that need two passages, or questions using different words from the docs.
   - 8 out-of-scope questions the documents cannot answer, where the correct response is "I don't know."
1. Measure retrieval with code: hit rate at 5 and MRR over the answerable questions.
1. Measure answers:
   - **Faithfulness:** whether every claim is supported by the retrieved passages, using an LLM judge with a binary verdict and a reason.
   - **Correctness:** whether the answer matches the reference answer, using an LLM judge or code where possible.
   - **Refusal accuracy:** the share of out-of-scope questions that got "I don't know," and the share of answerable questions that were wrongly refused.
1. Validate your judges. Label at least 40 outputs yourself for faithfulness and correctness before looking at the judge's verdicts. Report how often each judge agreed with you, and its true positive and true negative rates. Revise the judge prompt at least once if agreement is below 85%, and report the new numbers on labels you did not use while revising.
1. Produce a results report (Markdown or HTML generated by the harness) with every metric, broken down by question type, plus a list of the failing questions with their outputs.
1. Run error analysis on the failures: categorize them, count each category, and choose one change to your RAG system aimed at the largest category (for example, chunk size, contextual retrieval, the number of reranked results, or the answer prompt).
1. Make that one change, rerun the full harness, and add a before-and-after table to your report. List the questions that improved and the ones that regressed. Run both versions at least twice and say whether the difference is larger than the run-to-run variation.
1. Make the harness runnable with one command, and record the cost of a full run in tokens or dollars.
1. Push your project to GitHub with a README that explains what it does, how to run it, and what you learned.

#### Extra credit

- Run the harness automatically in a GitHub Actions workflow on every push to your Chat With Your Docs repo, and fail the build if faithfulness drops below a threshold.
- Compare two models for answer generation on quality and cost per question.
- Generate extra test questions with a model, then review and fix every one by hand, and report how many generated questions you had to throw away.

</div>

### Submitting your work

A strong README leads with the before-and-after table and a one-paragraph explanation of what you changed and why. It includes your judge agreement numbers, a few example failures with your error categories, and clear instructions for reproducing a run. Readers should come away trusting your numbers because you showed how you checked them.
