### Introduction

In this project you'll land a real contribution in an open source AI or agent library: find a good first issue, talk to the maintainers, submit a pull request with tests or docs, work through review, and write a short post about the experience. The goal is a merged PR. If the review is still going when you finish, a PR you have iterated on seriously in response to maintainer feedback also counts.

This is evidence no tutorial can give you: that you can work in someone else's codebase, to their standards, with their review.

### Before you start

- Choose a library you've actually used. Good candidates include [LangChain](https://github.com/langchain-ai/langchain), [LlamaIndex](https://github.com/run-llama/llama_index), [Pydantic AI](https://github.com/pydantic/pydantic-ai), [promptfoo](https://github.com/promptfoo/promptfoo), [Langfuse](https://github.com/langfuse/langfuse) or an MCP SDK such as the [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk). Any actively maintained AI or agent project with recent merged PRs from outside contributors is fine.
- Check that the project is healthy: PRs from outside contributors were merged in the last month, and issues get replies.
- Read its CONTRIBUTING guide and code of conduct, fork it, and get its test suite passing locally before you pick an issue.
- Create a small repo named `mimir-first-merged-pr` to hold your notes, your post draft and links. The contribution itself lives in the upstream project.

<div class="lesson-note lesson-note--warning" markdown="1">

#### Be a good guest

Maintainers are often volunteers. Don't open AI-generated PRs you don't understand, don't claim several issues at once, and don't ping people repeatedly. Many projects now close low-effort PRs on sight. One careful, small PR is worth more than five rushed ones.

</div>

### Assignment

<div class="lesson-content__panel" markdown="1">

1. Find an issue labeled "good first issue," "help wanted" or similar, or a small bug or documentation gap you hit yourself while using the library (open an issue for it first). Record the issue link and why you chose it in your notes.
1. Comment on the issue before you start: say you'd like to work on it and describe your planned approach in two or three sentences. Wait for a maintainer's go-ahead if the project's guide asks for one.
1. Make a focused change on a branch in your fork. It must include tests for code changes, or be a documentation change that you've built and checked locally. Run the project's full test and lint commands and confirm they pass.
1. Open a pull request that follows the project's template and conventions. Link the issue, explain what changed and why, and describe how you tested it.
1. Respond to review. Make requested changes promptly, reply to every comment, and keep a log in your notes of each round of feedback and what you learned from it.
1. Get the PR merged, or, if it's still in review when you finish, show at least one full round of iteration on maintainer feedback.
1. Write and publish a short post (400 to 800 words) on your Portfolio Site about the contribution: the issue, what you had to learn about the codebase, the review feedback, and what you'd do differently. Link the PR.
1. Push your notes repo to GitHub with a README that links the issue, the PR, the post, and summarizes what you learned.

#### Extra credit

- Land a second PR in the same project, ideally one a little larger than the first.
- Review someone else's PR in the project constructively, or help answer an issue.
- Contribute an example or integration that connects the library to one of your own projects.

</div>

### Submitting your work

A strong submission links a PR that a reviewer could read without context: small, focused, tested, well described, and with polite, prompt responses to review. The post is honest about what was hard. Add the merged PR to your resume and your Portfolio Site's About section; it's one of the most credible lines you can have.
