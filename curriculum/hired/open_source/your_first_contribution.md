### Introduction

A merged pull request in a library other engineers use is strong evidence. It shows you can read an unfamiliar codebase, follow a project's conventions, take review feedback, and ship something a maintainer was willing to accept. In AI, where many of the tools you've used are open source, it also puts you in contact with the people building them.

This lesson covers how to find a good first issue, how to approach maintainers, and how to get a pull request (PR) merged, building on what you learned in Branches and Pull Requests.

### Lesson overview

This section contains a general overview of topics that you will learn in this lesson.

- Why open source contributions help you get hired.
- The fork, branch, pull request workflow.
- Reading a project's README, CONTRIBUTING guide and code of conduct.
- Finding good first issues in AI and agent libraries.
- Communicating with maintainers before and during a PR.
- Handling review and what to do when a PR stalls.

### Key ideas

- **Contributions are evidence employers can check.** A merged PR is public, reviewed by experts and attached to your name.
- **The workflow is fork, branch, change, test, PR.** Fork the repo, clone your fork, create a branch, make a focused change, run the project's tests and linters locally, push, and open a PR against the original repo that links the issue.
- **Read the contributing guide first, every time.** It tells you how to set up the project, run tests, format code, write commits and whether you need to sign a contributor agreement. Ignoring it is the fastest way to get a PR closed.
- **Look for issues labeled "good first issue" or "help wanted"** in tools you've actually used: agent frameworks, eval tools, observability tools, MCP SDKs. Documentation fixes, missing tests, clearer error messages and small bugs you hit yourself are all valid first contributions.
- **Comment before you start.** Ask whether the issue is still open to work on and briefly describe your plan. This avoids duplicate work and wasted effort, and maintainers appreciate it.
- **Keep PRs small and well described.** One change per PR, with tests or docs, a clear description of what and why, and how you tested it. Small PRs get reviewed; large ones sit.
- **Review is a conversation, not a judgment.** Respond politely, make requested changes promptly, and ask when you don't understand. If a PR goes quiet for a week or two, a short, friendly follow-up is fine.
